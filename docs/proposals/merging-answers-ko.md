# 두 사람의 답을 합치는 법 — 리서치와 대안

> 질문: "상대와 나의 답을 어떻게 쉽게 합칠 수 있을까? 간편하게 결과를 낼 수 있으면 좋겠는데."
> 대상: `site/` (lovemedialogue.com). 지금은 서버가 없습니다.
> 관련: `docs/proposals/together-service-ko.md` (링크 3종), `docs/MILESTONES.md` (M1/M2 경계)

## 1. 지금 무엇이 불편한가 — 두 개의 다른 문제

"쉽게 합치기"와 "간편하게 결과"는 같은 문제가 아닙니다. 나눠 봐야 답이 나옵니다.

### 1-1. 합치기 — 왕복이 두 번이고, 시작한 사람이 제일 늦게 봅니다

지금 흐름을 실제 단계로 세면 여섯 단계입니다.

```
1. A가 100문항 답한다                         (~1시간)
2. A가 "내 답 링크"를 만들어 B에게 보낸다      (158자)
3. B가 링크를 열고 100문항 답한다              (~1시간)
4. B 화면에 비교 결과가 열린다                 ← B는 여기서 끝
5. B가 "비교 링크"를 만들어 A에게 되보낸다     (271자)
6. A가 그 링크를 열어야 비로소 결과를 본다     ← A는 B가 보내줘야만 본다
```

문제는 4번과 6번 사이입니다. **먼저 시작하고 먼저 답한 A가 마지막에 보고, 그것도 B가 되보내 줘야
봅니다.** B가 그 버튼을 안 누르면 A는 영원히 못 봅니다. 그리고 순서가 강제됩니다 — B는 A의 링크를
받기 전에는 비교를 열 수 없습니다. 각자 따로 답해 두고 나중에 합치는 것이 안 됩니다.

측정값 (100문항 기준, 실제 코드로 확인):

| | 길이 |
|---|---|
| 내 답 링크 | 158자 |
| 비교 링크 (두 사람) | 271자 |

### 1-2. 결과 — 100문항을 다 답해야 볼 것이 생깁니다

이쪽이 더 큽니다. 두 사람이 각자 한 시간씩, 합쳐서 **두 시간을 쓴 뒤에야** 첫 비교 화면이 열립니다.
그 전까지 이 제품은 "재미있어 보이는데 언제 뭐가 나오지" 상태입니다.

결혼 준비 중인 두 사람에게 각자 한 시간을 먼저 요구하는 것은, 그 자체로 대부분을 걸러 냅니다.

## 2. 다른 서비스는 어떻게 하는가 — 리서치

찾아본 것: 커플 문답·퀴즈 앱(Paired, Couple Game/Duo Quiz류), 한국의 우정테스트·밸런스게임 링크
서비스, 교실용 퀴즈(Kahoot, Quizizz), 결혼 전 진단 도구(Prepare/Enrich).

| 서비스 | 합치는 방법 | 계정 | 서버 |
|---|---|---|---|
| **Paired** | 페어링 코드를 만들어 상대에게 전달 → 상대가 앱에서 입력 | **양쪽 다 필요** | 필요 |
| 커플 퀴즈 앱 일반 | 코드 입력 또는 초대 링크 | 양쪽 다 필요 | 필요 |
| 한국 우정테스트류 | 내가 문제를 만들면 링크가 생기고, 친구가 풀면 **내 쪽에 쌓임** | 대개 불필요 | 필요 |
| **Kahoot / Quizizz** | 룸 코드(PIN), 링크, QR | 불필요(참가자) | 필요 |
| **Prepare/Enrich** | 각자 따로 검사 → 결과가 **상담사에게** 감 | 필요 | 필요 |

**핵심 발견 하나:** 로그인 없이 웹에서 두 사람의 답을 합쳐 주는 서비스를 찾지 못했습니다.
"간편한" 쪽은 예외 없이 서버에 답을 저장합니다. 이유는 명백합니다 — A와 B가 다른 시간에 답하는
이상, 그 사이에 답을 들고 있을 자리가 어딘가에는 있어야 하기 때문입니다. 서버가 없으면 그 자리는
**링크 그 자체**뿐이고, 그래서 링크가 손으로 오가야 합니다.

**핵심 발견 둘:** 그 서비스들의 대다수는 우리가 하려는 것과 목적이 다릅니다. 우정테스트는 "누가
나를 제일 잘 아는가"를 **채점**하고, 커플 퀴즈는 **맞히기** 게임입니다. 우리는 점수를 매기지 않기로
한 제품이라 그쪽 설계를 그대로 가져올 수 없습니다. 가져올 수 있는 것은 *합치는 기계 장치*뿐입니다.

**핵심 발견 셋:** Prepare/Enrich는 "각자 따로, 미리 맞춰 보지 말고" 답하게 한 뒤 결과를 제3자에게
보냅니다. 우리의 "내가 답하기 전에는 상대 답이 안 보인다" 규칙과 같은 발상이고, 이 규칙은 지켜야
합니다. 아래 대안은 전부 이 규칙을 깨지 않습니다.

## 3. 대안

서버 없이(M1) 할 수 있는 것 다섯, 서버가 있어야 하는 것 하나.

### 대안 A — 같이 하기 모드: 폰 하나를 주고받는다 ★ 추천

**합치는 문제를 없애 버립니다.** 링크도, 코드도, 서버도 필요 없습니다.

```
문항 1 → A가 고른다 → [상대에게 넘기기] → 화면이 가려진다
       → B가 고른다 → 두 답이 함께 열린다 → 이야기한다 → 다음 문항
```

- 한 기기에서 번갈아 답하므로 합칠 것이 애초에 없습니다
- **문항마다 즉시 결과가 나옵니다.** 두 시간이 아니라 30초
- 마주 앉아 이야기하려고 만든 질문집이니, 이게 원래 쓰임에 가장 가깝습니다
- 먼저 고른 사람의 답은 넘기는 순간 가려집니다 — 공개 규칙이 그대로 지켜집니다
- 답은 두 벌로 저장되고, 끝나면 기존 결과지가 그대로 열립니다

**한계:** 두 사람이 같은 자리에 있어야 합니다. 떨어져 있으면 못 씁니다.
**드는 것:** 화면 하나(가림막 + 넘기기 버튼), 저장소에 "나/상대" 두 벌. 서버 변화 없음.

### 대안 B — 파트 단위로 주고받는다 ★ 추천

100문항을 한 덩어리로 보지 않고 **10문항짜리 한 파트**를 한 번의 교환 단위로 씁니다.

- 첫 결과까지 **두 시간 → 4분**
- 파트마다 결과가 나오니 "다음 파트도 해보자"가 생깁니다
- 링크가 짧아집니다: 파트 하나면 payload 8자, 링크 60자 안팎
- 열 번 나눠 보내는 것이 아니라, **원할 때 지금까지 답한 만큼만** 보내는 것으로 설계하면 교환
  횟수는 두 사람이 정합니다

**한계:** 여러 번 주고받게 될 수 있습니다. 다만 매번 결과가 나오므로 왕복이 비용이 아니라 진행입니다.
**드는 것:** 링크에 "어디까지 답했는지"를 담고, 비교 화면이 부분 비교를 다루게 하기. 이미 부분
비교는 됩니다(둘 다 답한 것만 열림) — 실제로는 **"지금까지 것 보내기" 버튼과 문구**가 대부분입니다.

### 대안 C — 코드 붙여넣기: 순서를 없애고 왕복을 되돌린다 ★ 추천

지금은 비교가 **URL의 `#` 뒤에서만** 열립니다. 그래서 링크를 받은 사람만 비교를 볼 수 있고,
순서가 강제됩니다. 결과지에 **붙여넣기 칸**을 하나 두면:

- 두 사람이 **각자 아무 때나** 답하고, 나중에 아무나 상대 코드를 붙여넣으면 비교가 열립니다
- "누가 먼저 보내야 하는가"가 사라집니다
- 카톡으로 온 코드를 복사해 붙이는 것은 링크를 여는 것과 비슷한 수고입니다
- 그리고 **B가 답을 마치는 순간 "A에게 결과 보내기"를 자동으로 띄우면** 1-1의 6번 문제가
  줄어듭니다 — 지금은 B가 스스로 찾아 눌러야 합니다

**한계:** 붙여넣기는 링크 열기보다 한 단계 낯섭니다. 링크 방식과 **둘 다** 두면 됩니다.
**드는 것:** 입력칸 하나, 기존 `decodeShare` 재사용. 작습니다.

### 대안 D — QR 코드

마주 앉았을 때 서로의 화면을 찍으면 합쳐집니다. 전송 앱이 필요 없습니다.

**한계:** 마주 앉았다면 대안 A가 더 낫습니다. QR은 "같이 있지만 각자 자기 폰으로 답하고 싶다"는
좁은 경우에만 이깁니다. 그리고 271자를 QR에 담으면 밀도가 높아 구형 카메라가 힘들어합니다.
**판단:** 대안 A를 하면 우선순위가 낮습니다.

### 대안 E — 링크 압축

문항당 1자를 비트로 눌러 담습니다. 측정:

| | payload | 링크 |
|---|---|---|
| 지금 | 100자 | 158자 |
| 3비트 패킹 | 52자 | 110자 |
| 5진수 최적 패킹 | 40자 | 98자 |

**판단:** 부수적입니다. 158자도 카톡에서 문제없이 갑니다. 체감을 바꾸지 않습니다. 다만 200제가
나오면 그때는 필요합니다. **지금 하지 말 것.**

### 대안 F — 서버 (M2)

초대 링크 하나로 끝납니다. 둘 다 답하면 각자 자기 기기에서 같은 결과를 봅니다. 되보낼 것도,
붙여넣을 것도 없습니다. 리서치한 서비스가 전부 이렇게 하는 데는 이유가 있습니다.

**대가가 작지 않습니다:**

- 계정 또는 최소한 익명 세션 — 그리고 그 순간 개인정보 처리 대상이 생깁니다
- 처리방침을 **다시 써야** 합니다 (보관 기간·동의·파기). M1 처리방침은 "브라우저에만 저장"으로
  쓰여 있고, 그 문장이 지금 애드센스 심사를 기다리고 있습니다
- "흔적 없이 떠날 수 있다"는 `site/answers.js`가 명시적으로 내건 안전 약속이 약해집니다 — 이 질문집
  특성상 통제적인 관계에 있는 사람이 답할 수 있다는 전제로 쓴 규칙입니다
- M2 서버 코드는 **이미 대부분 존재합니다**(닫힌 PR #71). 없는 것은 결정입니다

**판단:** M2에서 합니다. M1을 여기에 태우지 않습니다.

## 4. 권고

**M1에서 A + C를 하고, B를 문구로 얹습니다.**

| 순서 | 무엇 | 왜 이 순서인가 | 크기 |
|---|---|---|---|
| 1 | **A. 같이 하기 모드** | 합치기 문제를 없애고, 첫 결과가 30초로 당겨집니다. 이 제품의 본래 쓰임 | 화면 하나 |
| 2 | **C. 붙여넣기 + 자동 되돌리기** | 떨어져 있는 경우의 순서 강제와 "A가 못 보는" 문제를 같이 해결 | 작음 |
| 3 | **B. 지금까지 것 보내기** | 100문항을 다 채워야 한다는 압박을 없앰. 대부분 문구 작업 | 작음 |
| — | E. 압축 | 200제가 나오면 | 보류 |
| — | D. QR | A를 하면 거의 필요 없음 | 보류 |
| M2 | F. 서버 | 진짜 "간편". 처리방침을 다시 쓰는 각오와 함께 | 큼 |

이유를 한 줄로: **서버 없이 "합치기"를 쉽게 만드는 데는 상한이 있지만, "합칠 필요를 없애는" 데는
상한이 없습니다.** 리서치한 서비스들이 전부 서버를 쓰는 것은 떨어져 있는 두 사람을 전제했기
때문인데, 결혼 준비 중인 두 사람은 상당수 같이 있습니다. 거기서는 폰 한 대가 서버보다 낫습니다.

## 5. 열린 결정

1. **같이 하기 모드에서 두 사람의 답을 어떻게 저장하는가.** 한 브라우저에 두 벌을 두면 "내 답"과
   "상대 답"의 구분이 생깁니다. 지금 저장소는 한 벌만 상정합니다
2. **한 문항씩 번갈아 갈 것인가, 한 파트씩 갈 것인가.** 문항마다 폰을 넘기면 대화가 자주 끊깁니다.
   파트(10문항)씩 넘기면 흐름은 낫지만 첫 결과가 5분 뒤입니다
3. **붙여넣기 칸을 결과지에만 둘 것인가, 질문 페이지에도 둘 것인가**
4. F를 언제 시작할 것인가 — M1 광고 심사가 끝난 뒤인가, 병렬인가 (`docs/MILESTONES.md`는 병렬)

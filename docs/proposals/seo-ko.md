# SEO 극대화 — 감사와 제안

> 질문: "SEO 극대화를 위한 개선 제안해줘."
> 대상: `site/` (lovemedialogue.com), 배포본 `608d684` 기준
> 관련: `docs/OWNER_ACTIONS.md` X5e(서치콘솔)·X7(애드센스), `docs/MILESTONES.md` M1

## 측정 방법과 한계

이 문서의 숫자는 전부 **빌드 산출물(`site/dist/`)을 직접 읽어서** 잰 값입니다. 배포된 것과
같은 빌드입니다.

한계를 먼저 적습니다. **이 환경의 아웃바운드 프록시가 `lovemedialogue.com`을 막고 있어
(CONNECT 403) 실제 서비스 페이지도, 검색 결과도 열어볼 수 없었습니다.** 그래서 *지금 몇 개가
색인되어 있는지, 어떤 질의에서 몇 위인지는 이 문서에 없습니다.* 그건 서치콘솔·서치어드바이저를
붙인 다음에야 알 수 있고, 붙이는 것 자체가 아래 제안 중 하나입니다.

## 0. 지금 무엇이 있고 무엇이 없나

있는 것부터. 이 사이트는 SEO 기본기가 이미 상당히 좋습니다 — 없는 것만 나열하면 실제보다
나쁘게 읽히므로 먼저 적습니다.

- **정적 HTML.** 질문 100개가 전부 마크업에 있습니다. 자바스크립트를 꺼도 다 읽힙니다
- `<html lang="ko">`, 페이지마다 고유 canonical, `rel=prev`/`rel=next`로 이어진 10쪽
- 질문 페이지마다 `ItemList` + `Question` JSON-LD (정답이 없는 질문이므로 `acceptedAnswer`가
  아니라 `suggestedAnswer` — 정직한 선택입니다)
- 결과지는 `noindex`, 사이트맵에서도 빠져 있음 (개인 페이지이므로 맞습니다)
- robots.txt가 사이트맵을 가리킴, HTTPS 전용, 폰트 preload, 이미지 lazy-load
- **본문 자체가 롱테일 그 자체입니다.** "부부 사이 휴대전화 비밀번호는 어떻게 다루는 것이
  편안할까요?" 같은 문장 100개 — 돈 주고도 못 만드는 질의 매칭입니다

색인 대상 URL은 **13개**입니다. 질문 10 + 소개·문의·처리방침 3.

## 1. 결함 — 고치면 바로 이득, 위험 없음

### 1-1. 사이트맵에 홈이 없습니다

```
site/dist/sitemap.xml → 13 URL
/marriage/ … /marriage/10/, /about/, /contact/, /privacy/
```

`https://lovemedialogue.com/` 이 없습니다. 사이트에서 권위가 가장 높고 다른 모든 페이지가
링크하는 페이지가 사이트맵에서 빠져 있습니다.

원인은 `scripts/build-site.mjs:88`입니다 — `sitemapXml([...pages, ...standing])`. 홈은 `pages`
에도 `standing`에도 없습니다. **한 줄입니다.**

### 1-2. 홈에 meta description도 OG 태그도 없습니다

`renderIndex`는 `headTags()`를 쓰지 않고 `<title>`과 canonical만 직접 씁니다
(`site/render.js:748`). 그 결과 홈의 `<head>`에는 이것뿐입니다:

```html
<title>Love Me · 다가올 삶을, 함께 준비하다.</title>
<link rel="canonical" href="https://lovemedialogue.com/">
```

- `description` 없음 → 검색 결과의 두 줄을 구글이 알아서 긁어 씁니다
- `og:*` 전부 없음 → 카카오톡·네이버·슬랙에 홈 링크를 붙이면 **제목만 나오는 맨 카드**
- 제목이 브랜드로 시작 → "Love Me"를 아는 사람만 찾을 수 있는 제목입니다

### 1-3. og:image가 사이트 전체에 하나도 없습니다

```
og:image 태그 수: 0
twitter:card: summary   (summary_large_image 아님)
```

이 사이트의 유통 경로가 **"상대에게 링크를 보낸다"** 하나라는 걸 생각하면 이게 가장 아픕니다.
「함께 풀기」로 만든 초대 링크가 카카오톡에 붙는 순간 회색 빈 카드가 뜹니다. 상대가 누를
이유가 그만큼 줄어듭니다.

브랜드 자산은 이미 있습니다 — `brand/mark.png`, 장면 그림 6장. `scripts/build-brand-assets.py`
가 1200×630 공유 카드를 팩별로 한 장씩 굽고, `headTags`가 그걸 가리키면 됩니다.

## 2. 검색 노출을 실제로 늘리는 것

### 2-1. 파트 10개가 제목·설명상 거의 중복입니다 ← **가장 큰 온페이지 이득**

지금:

| 쪽 | title | description |
|---|---|---|
| 5 | `결혼 100제 (5/10) · Love Me` | `결혼 100제 5쪽. 41번부터 50번까지의 질문입니다.` |
| 6 | `결혼 100제 (6/10) · Love Me` | `결혼 100제 6쪽. 51번부터 60번까지의 질문입니다.` |

숫자만 다릅니다. 검색 엔진 입장에서 이 열 페이지는 서로를 구별할 근거가 거의 없고, 사람
입장에서도 검색 결과에서 5쪽을 누를 이유가 없습니다.

**그런데 팩 데이터는 이미 파트 이름과 한 줄 소개를 들고 있습니다.** `pageModel().part`:

```js
{ number: 5, title: "우리 사이의 경계",
  blurb: "신뢰와 자유가 함께 머물 수 있도록 애매했던 선을 말로 만들어요." }
```

이걸 쓰기만 하면 됩니다:

| | 지금 | 제안 |
|---|---|---|
| title | `결혼 100제 (5/10) · Love Me` | `우리 사이의 경계 — 결혼 100제 5부 · Love Me` |
| description | `결혼 100제 5쪽. 41번부터…` | `신뢰와 자유가 함께 머물 수 있도록 애매했던 선을 말로 만들어요. 결혼 전 나눠 볼 질문 10가지.` |
| h1 | `결혼 100제` (10쪽 전부 동일) | `결혼 100제` 유지 + 파트명을 h1으로 올릴지는 판단 필요 |

고칠 곳은 `site/seo.js`의 `pageTitle`·`pageDescription` 두 함수뿐입니다. 파트 이름 열 개 —
"우리 둘의 작은 세계", "한집의 리듬", "돈이 말해주는 마음", "사랑 밖의 사람들",
"우리 사이의 경계", "다투고 다시 손잡는 법", "서로의 꿈과 일", "아이를 생각하는 시간",
"예상하지 못한 계절", "평생이라는 여운" — 이 그대로 열 개의 서로 다른 질의 표면이 됩니다.

h1은 신중하게 봐야 합니다. 지금 모든 페이지의 h1이 `결혼 100제`이고 파트명은 h2입니다.
h1을 파트명으로 바꾸면 페이지 고유성은 올라가지만 팩 이름이 h1에서 사라집니다. **h1은
`결혼 100제 · 5부 우리 사이의 경계`처럼 둘 다 담는 쪽을 권합니다.**

### 2-2. 네이버 서치어드바이저 — 아직 안 붙었습니다

한국어 서비스에서 네이버를 빼놓는 건 유입 경로 하나를 통째로 닫아 두는 일입니다 — 정확한
점유율은 조사마다 다르고 여기서 숫자를 지어내지 않겠습니다만, 무시할 수 있는 크기가 아닌
것은 분명합니다. 네이버는 자체 웹마스터 도구
(서치어드바이저)에 **소유 확인 메타 태그**를 넣고 사이트맵을 따로 제출해야 수집을 시작합니다.
네이버는 공유 카드도 OG 태그를 읽으므로 1-3과 붙어 있습니다.

구현은 `SITE.naverVerification` 한 줄 + `headTags`에서 홈에만 출력. **구글 서치콘솔(X5e)도
아직 미완입니다** — 둘 다 소유자만 할 수 있는 일이고, 코드 쪽 준비는 한 줄이면 끝납니다.

팩을 새로 발행할 때마다 두 곳 모두에 사이트맵을 다시 제출해야 합니다 — 자동으로 되지
않습니다.

### 2-3. 「질문 개선 피드백 DEBUG」가 페이지 텍스트의 22%입니다

측정 (`/marriage/5/`):

```
페이지 전체 보이는 텍스트   4,396자
q-feedback 블록 10개         980자   = 22%
블록을 빼면                 3,406자
```

문항마다 이 문장이 붙습니다:

> **질문 개선 피드백** `DEBUG`
> 상황이 현실적인지, 네 선택지가 한 축에서 넓고 겹치지 않는지, 대화가 자연스럽게 깊어지는지
> 평가해 주세요.

열 페이지 전부에 100번 반복됩니다. 문제는 세 가지입니다.

1. 페이지 텍스트의 22%가 질문과 무관한 문구 — 주제 신호가 그만큼 희석됩니다
2. **열 페이지에 걸쳐 완전히 동일한 보일러플레이트** — 1-2의 중복 문제를 키웁니다
3. `DEBUG`라는 글자가 공개 페이지에 있습니다. 애드센스 심사자도 봅니다

**이건 이미 예정된 작업입니다.** 소유자가 "팩을 다 읽어 본 뒤에 뺀다"고 하셨고,
`SITE.debugFeedback = false` 한 줄이면 전 페이지에서 사라집니다. 여기서는 *SEO 비용이
생각보다 크다*는 것만 숫자로 적어 둡니다.

### 2-4. 구조화 데이터 — 절반만 있습니다

| 페이지 | 지금 | 제안 |
|---|---|---|
| 질문 10쪽 | `ItemList` + `Question` ✅ | + `BreadcrumbList` |
| 홈 | 없음 | `WebSite` + `Organization` |
| 소개·문의·처리방침 | 없음 | `WebPage` (최소) |

- **`Organization`** — 상호 `afterscent`, 대표자, 주소, 문의 메일이 이제 다 있습니다.
  처리방침에 이미 적혀 있는 그 값들을 기계가 읽을 수 있는 형태로 한 번 더 내보내는 것이고,
  브랜드 질의("러브미 다이얼로그")에서 지식 패널로 이어지는 유일한 경로입니다
- **`BreadcrumbList`** — 검색 결과에서 URL 대신 `Love Me › 결혼 100제 › 5부`로 표시됩니다.
  10쪽짜리 시리즈에서 클릭률에 직접 붙습니다
- `FAQPage`는 **권하지 않습니다.** 구글이 2023년에 FAQ 리치 결과를 정부·보건 사이트로
  제한했습니다. 지금 붙여도 표시되지 않고, 형태상 이 질문들은 FAQ도 아닙니다
  (자주 묻는 질문이 아니라 서로에게 던지는 질문입니다)

### 2-5. 사이트맵에 `lastmod`이 없습니다

지금은 URL만 있습니다. `lastmod`가 있으면 크롤러가 *무엇이 바뀌었는지* 알고 재방문 예산을
바뀐 페이지에 씁니다. 팩이 늘어날수록 값이 커집니다. 빌드 시각이 아니라 **콘텐츠가 실제로
바뀐 시각**이어야 의미가 있습니다 — 빌드 시각을 넣으면 매 배포마다 전 페이지가 바뀐 것처럼
보이고, 그건 신호가 아니라 소음입니다. 팩 데이터의 해시나 git 커밋 시각이 근거가 됩니다.

### 2-6. 404 페이지가 없습니다

`site/dist/404.html`이 없어서 GitHub Pages의 기본 404가 뜹니다. 브랜드도 없고 돌아갈 링크도
없습니다. 오타 URL·죽은 외부 링크가 그대로 이탈이 됩니다. 홈과 팩 목록으로 가는 링크가 있는
404 한 장이면 됩니다.

## 3. 가장 큰 레버이자 가장 느린 것 — 콘텐츠 양

색인 대상 페이지가 **13개**입니다. 이건 SEO 기법으로 넘을 수 있는 벽이 아닙니다.

`docs/OWNER_ACTIONS.md` X7이 애드센스에 대해 이미 같은 말을 하고 있습니다 — "ten Parts is on
the low side for review". 색인도 똑같습니다.

- **`pregnancy-100`은 이미 만들어져 있고 등록되어 있습니다.** 발행은 `site/config.js`의
  `PUBLISHED`에 항목 하나입니다. 그것만으로 13 → 23쪽. 발행할지 말지는 D6/N7과 얽힌
  소유자 결정이라 여기서 정하지 않습니다
- 홈의 홀더 5개(연애·임신·출산·교육·노후)는 색인 가치가 0입니다 — 제목도 링크도 없는 그림
  이니까요. **그게 의도된 설계이고 바꾸자는 게 아닙니다.** 다만 SEO 관점에서 저 다섯 칸은
  아직 비어 있는 칸이라는 것만 적어 둡니다

### 질문 하나당 페이지로 쪼개는 건 권하지 않습니다

100개 URL이 생기니 매력적으로 보이지만, 각 페이지가 질문 한 줄 + 선택지 네 개 = 200자
남짓이 됩니다. 얇은 페이지 100개는 색인에서 통째로 버려지기 쉽고, 무엇보다 **10문항씩 이어서
답하는 지금의 읽기 경험이 무너집니다.** 지금의 10쪽 구조가 SEO와 UX 둘 다에서 옳습니다.

## 4. 성능 — 재기 전에는 손대지 않는 것을 권합니다

Core Web Vitals는 순위 요소이긴 하지만 작은 요소이고, 이 사이트는 이미 정적 HTML입니다.
현재 값:

| | 크기 |
|---|---|
| 질문 페이지 HTML | 56.1 KB |
| `site.css` | 43.7 KB |
| 폰트 4종 (MaruBuri 400/600, Pretendard 400/600) | 284.7 KB |

`site.css` 43.7KB가 렌더 차단이라는 점, 폰트 4종 중 2종만 preload된다는 점이 눈에 띄지만,
**실측 없이 손대면 잃을 게 더 큽니다.** 서치콘솔을 붙이면 실제 사용자 데이터(CrUX)가 들어오고,
그때 고칠 곳이 있으면 그때 고치는 것이 맞습니다. 지금 크리티컬 CSS를 인라인하는 건 추측입니다.

| 6 | 404 페이지 | 작음 | 코드 |
| 7 | 사이트맵 `lastmod` | 중간 | 코드 |

1~7의 효과를 확인할 방법이 없습니다** — 무엇이 색인됐는지, 어떤 질의로 들어오는지 볼 창이
그것뿐입니다. 10·11은 판단이 필요합니다.
